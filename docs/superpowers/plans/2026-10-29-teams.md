# Teams Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Crew bots become teammates in teams that live in Tether (Phase 1), a Telegram group (Phase 2) or a Slack channel (Phase 3): pinged, handed tasks and loops, handing work to each other, shipping through runs, gates, approvals and GitHub PRs.

**Architecture:** One `Teams` service (`src/teams/`) sits on top of what exists: a ping is an assistant `runTurn` with the agent's persona, a task is an engine workflow run on the agent's binding, a loop is a Goal owned by agent + team, approvals are engine approval nodes (task runs) or team cards (loop ship, proposals, goal asks), memory is the bot's lessons with a team tag. Phases 2 and 3 add a transport each (Telegram long polling, Slack Socket Mode) that maps platform events onto the same `Teams.post` / `Teams.decide` calls and renders the same messages natively.

**Tech Stack:** TypeScript (Node ≥ 22.12, node:sqlite, global fetch/WebSocket), React 19 + Vite, vitest (node + jsdom projects).

**Spec:** `docs/superpowers/specs/2026-10-29-teams-design.md` (approved; §6.3, §8, §10 settled). Boards: `docs/design/teams/{Sidebar,Main,NewTeam,Agent,Slack,Telegram}.dc.html`.

## Global Constraints

- Agents = Crew bots + `specialty` (≤ 24 chars) + `personality` (≤ 500 chars) + memory (the bot's lessons). No second agent list, no second lesson store.
- Memory: ≤ 200 lessons per agent (existing `MAX_LESSONS_PER_BOT`), oldest dropped; a team lesson is never a quote and never says who said what; per-lesson delete and Forget all; a team setting "don't learn from this team" (`learn: false`, default on).
- Team: `{ id, name, place: 'tether'|'slack'|'telegram', link?, project, agents: botId[], people, approvers: 'any'|personId[], level: 'tight'|'balanced'|'loose', limits: { usdPerDay, runsPerDay }, learn }`, stored under `<home>/teams/`, files 0600.
- Levels: Tight = plan approval and result approval; Balanced (default) = approve before ship; Loose = ship when gates pass, within limits.
- Ship = push the run's branch + open a GitHub PR through `gh` with the connected account (`ghExec`); merge only when an allowed approver tells the agent to and the PR's checks pass.
- The approver rule is checked on every approve, reject and merge, whatever surface it comes from.
- Limits: when `usdPerDay` or `runsPerDay` is reached nothing new starts (answers, runs, loop runs); in-flight runs finish under their own run budget.
- Message text from any surface is untrusted: fenced in prompts, agents act only through runs with gates, approvals and limits.
- Secrets only in the secret store; never in config, logs, argv, URLs or API responses.
- Reuse runs, Goals, approvals, attention, assistant turns, lessons, accounts; no new runtime dependency.
- Web: Studio tokens (`--ink --mut --line --line2 --edge --s1 --s2 --acc --accBg --accInk --warn --warnBg --ok --okBg --bad --badBg --mono`), SideSection/SideRow, beui kit, Face/FaceStack, StepTrack, ApprovalCard, ActionNode; no purple, no gradients, no glow (`web/src/rules.test.ts`).
- Commits: plain conventional messages, no trailers.

## Review Focus

1. A Slack/Telegram place chosen in New team during Phase 1: the server refuses it (400 "connect in a later phase"); the form shows both disabled with that note.
2. A message that mentions no agent, or an agent not in the team: stored as a plain message, nothing runs (test in Task 7).
3. Two clicks on Approve (or Approve from the Inbox and from the team card): only one ship happens; the second gets 409 (test in Task 7).
4. The daily limit reached while a loop is mid-way: the loop pauses with the reason, the run in flight finishes, nothing new starts (test in Task 7).
5. `gh` missing, no `origin` remote, or a push refused: the ship posts a plain failure line and leaves the branch, never throws out of the watcher (test in Task 6).
